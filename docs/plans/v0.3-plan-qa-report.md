## 1. Corrections — apply these to the plan before execution

### QA-1 — `D1` severity is overstated: the caches are **per-connection**, not per-process

**Plan says:** "unbounded agent memory growth (~86 400 full job-list snapshots/day)",
"unbounded RSS growth in the process that also runs curl", severity **P0**.

**Actual:** `EngineService.swift:1556` — `/// Per-connection exported object`. A fresh
`EngineControlExporter` is constructed for every accepted connection
(`EngineService.swift:1569`, inside `shouldAcceptNewConnection`), and all 24 caches are
**instance** properties on it (`:51-75`). They die with the connection.

**Corrected claim:** growth is unbounded **over the lifetime of one XPC connection**, not
the agent process. `EngineClient` holds a single connection until invalidation or
interruption (`EngineClient.swift:93-104`), so a user with Flow open for 8 hours
accumulates ~28 800 `JobListSnapshot` objects on that one exporter — each containing
*every* job in the library. On reconnect it resets to zero.

**What does not change:** the hit rate is still provably 0 % — `EngineClient` mints a fresh
`UUID().uuidString` on every call (`:70, :180`, and 20 further sites) and never retries with
a reused ID. The caches purchase nothing. Deletion is still correct and still the largest
single removal in the plan.

**Actions:**
- Downgrade `D1` **P0 → P1**.
- Rewrite the evidence cell: "unbounded per-connection growth over a session; ~3 600
  full snapshots/hour while the app is open; reset on reconnect."
- Move `D1` out of the "biggest delete" headline framing as a *leak* — keep it there as
  the biggest delete by **line count and zero-value**, which is still true.
- The Phase 4 DoD item "agent RSS is flat over a 1-hour idle run" is **still the right
  test** — it measures exactly this. Keep it, but hold the app connection open for the
  full hour or the test passes vacuously.

### QA-2 — `S2` flap rate is understated (finding gets *stronger*)

**Plan says:** the starved job "flaps `downloading → queued` five times a second, writing
to SQLite each time."

**Actual:** each failed cycle writes **three** job states, not one —
`TransferOrchestrator.swift:208` (`connecting`), `:221` (`downloading`), `:259` (`queued`)
— before `:263` sleeps 200 ms and returns. `pump()` then re-fetches on its own 200 ms
cadence (`:163`). So each starved job cycles every ~200–400 ms and emits **~7–15 SQLite
writes per second**. With two starved jobs (the default 5-job / 96-socket / 32-per-host
configuration guarantees at least two), that is up to **~30 writes/second of pure churn**
on the sole writer, concurrent with curl.

**Action:** amend the `S2` evidence cell with the 3-writes-per-cycle detail. The fix and
the acceptance test are unchanged; the priority is if anything more justified.

## 3. Risks the plan under-weights

**R1 — Task 1.4 (work stealing) is the riskiest change in the release and the plan
treats it as one line item.** It rewires `curl_multi` lifecycle management in C while the
Swift `SegmentedTransfer` ledger concurrently mutates the same range set. Two specific
hazards the plan does not name:

- Adding an easy handle mid-loop must not race `SegmentLedger.resplit`, which mutates
  `entries` under `NSLock` (`SegmentedTransfer.swift:556-576`) while `record()` is being
  called from curl write-callback threads.
- Splitting a range that is *currently downloading* corrupts the `.segmap`. Only split
  ranges with **no live easy handle**.

Add an explicit sub-task: define who owns range ownership during a split, and add a
`Tests/Fuzz`-style randomised split/complete/abort test before the C change. `make test-tsan`
is listed but is not sufficient on its own — it will not catch a logically wrong split.

**R2 — Task 1.6 conflicts with the other plan.**
`docs/plans/codebase-architecture-performance-improvement-plan.md` P2/P3 rewrite the same
`fetchJobRows` / `listJobs` path with a different design (deep projection module +
sequence-correct delivery). Running both is a guaranteed rebase collision. **Decide which
plan owns that file before Phase 1 starts.** Recommendation: this plan takes only the
*filter* (cheap, ship-blocking for speed) and explicitly defers the projection rewrite.

**R3 — Phase 2 items 2.1 and 2.2 both add engine-state awareness to `LibraryModel`, from
two directions.** Sequence them as one commit or 2.2 will be written against a
`lastErrorMessage` binding that 2.1 is still moving.

**R4 — no rollback criteria.** Every Phase 1 task can regress correctness in ways the unit
suite will not catch (partial-file corruption surfaces days later on resume). Add to each
task: *"revert if the resume-after-kill test loses more than N bytes."* The plan measures
speed but only gates on correctness implicitly.

## 4. Gaps in the plan

**G1 — the `.segmap` write amplification is never examined.** `SegmentLedger.record`
(`SegmentedTransfer.swift:525-541`) writes the whole map as JSON at most once/second, and
`markCompleted` (`:543-551`) and `resplit` (`:556-576`) each force an unthrottled full
write. Work stealing (task 1.4) will call `resplit` far more often — potentially per
completed segment. With 32 entries that is a small JSON file, but it is an `options:
.atomic` write, i.e. a temp-file create + `rename` per call. Add a measurement to Phase 0
and a throttle to task 1.4 if it shows up.

**G2 — `preferredSegmentCount` caps at 32 with no justification and no experiment.**
`SegmentedTransfer.swift:33` — `min(32, max(8, totalBytes / 4 MiB))`. The plan fixes *when*
the cap is applied (S3) but never asks whether 32 is right. Phase 0 should sweep
8/16/32/64 against the capped fixture and pick from data. It is nearly free to add.

**G3 — no rate-limit / 429 behaviour test.** S3's fix is "only lower the hint on evidence
of refusal", but nothing in the plan or the test suite produces a 429. `FaultHTTPServer`
has a `/fixtures/status/<code>` route (`:180-183`) — wire it in.

**G4 — U8 (accessibility) is the only Phase 2 item whose acceptance is a manual pass, and
`AGENTS.md` lists manual VoiceOver as still open from the *previous* release.** It has now
slipped once. Either commit to it as a DoD blocker for v0.3 or move it to v0.4 explicitly —
do not carry it a third time.

## 5. Scoping opinion

Phase 1 (7 tasks, two of them C-level) plus Phase 2 (10 tasks) plus Phase 3 (9 commits) is
too much for one release cycle if the goal is a *confident* v0.3.

**Recommended cut:**

- **v0.3 = Phase 0 + Phase 1 tasks 1.1, 1.2, 1.3, 1.4 + Phase 2 items 2.1–2.3 + Phase 3
  steps 1–3.** That is: the four real throughput fixes, the three UX fixes that stop the
  app lying, and the three deletions with conclusive evidence.
- **Defer to v0.3.1:** 1.5 (shared TLS handle — real but second-order), 1.6 (collides with
  the other plan), 1.7, and Phase 2 items 2.4–2.10.
- **Rationale:** 1.1–1.4 are the entire speed story. 1.5–1.7 are latency and CPU polish
  that will not show up next to a fixed tail. Shipping them together dilutes the ability to
  attribute the speed win to anything.
