# Flow v0.3 — Speed, UX, Deletion Plan

Status: `IMPLEMENTED — uncommitted in the working tree, awaiting maintainer review`
Baseline commit: `ccdacdc` (`main`)
Handoff: `Artifacts/handoffs/v0.3-arch-slice-20260724T1846Z.md`

## Measured result — the number this plan existed to produce

`Tests/Performance/TransferThroughputTests.swift`, straggler-tail benchmark.
Identical conditions in both runs; one connection capped 8× slower than its peers.
The only variable is tiling:

| tiling | wall clock |
|---|---|
| coarse (`tiles == connections`) | 4.37 s |
| fine (`tiles = 8 × connections`) | 0.75 s |
| **speedup** | **5.83×** |

Finding S1 is now demonstrated rather than argued. Because the benchmark compares
two tilings under the same straggler, it cannot pass unless the refill loop is
genuinely reusing freed connection slots — a regression there collapses fine
tiling back to coarse behaviour and fails the test.
Review type: transfer hot path → UX surface → dead weight
Scope note: complements `docs/plans/codebase-architecture-performance-improvement-plan.md`,
which covers XPC/persistence architecture depth. **This document covers the network
transfer path, which that plan explicitly does not.** Overlap is called out per finding.

---

## 1. Executive verdict

**Biggest speed win:** the segmented transfer has no work stealing. `runSegmentedRanges`
blocks until *every* range in a pass finishes, so the last 10–30 % of every large file
runs on 1–3 connections while 29 sit idle — the exact failure mode IDM-class managers
exist to avoid. Second biggest is not in curl at all: the socket budget makes **only 3 of
the 5 allowed concurrent jobs runnable**, and a second download from the same host cannot
start — it flaps `downloading → queued` five times a second, writing to SQLite each time,
on the same process that runs curl.

**Biggest UX win:** `LibraryModel.lastErrorMessage` is published, written in 8 places, and
**rendered nowhere**. Every pause/delete/priority/engine failure in the board is silently
swallowed. Fix that one binding and the app stops lying about what happened.

**Biggest delete:** 24 per-RPC idempotency caches in `EngineService.swift` with **zero
eviction anywhere in the file**, fed by a client that mints a fresh `UUID` on every call.
Hit rate is provably 0 %; the only effect is memory that grows for as long as the app holds
its connection (~3 600 full job-list snapshots/hour). Deleting them removes ~300 lines of
pure cost.
